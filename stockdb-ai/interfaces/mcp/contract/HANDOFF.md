# 给 StockDB 服务维护 Agent 的实施任务

请先完整阅读同目录 `README.md`（合同 `stockdb-market-v3`，修订 `3.0.0`），
再读取 `contract.schema.json`、`examples.json`、`acceptance-cases.json`。
这些文件共同构成本项目未来行情客户端的实施依据。当前服务不宣称已经满足它们。

## 任务目标与范围

迭代现有NAS StockDB HTTP MCP行情服务，使 `core_daily_v1` 通过共同契约验收，
并保留原有未显式选择v3的客户端兼容。复用现有工具名，服务内部复用已有数据能力。
首批是沪深股票/ETF未复权日K、单票/批量、证券身份、日历、错误/来源/单位/时间/快照和有界失败恢复。
指数/板块、分钟、复权、全市场历史身份按合同逐项声明，未实现明确不支持。
本任务不要求财务、公告、新闻或策略服务，也不接收项目持仓、账户、成本、交易与私有研究数据。

## 开工前必须查证

1. 当前容器/服务、源码实际路径、Git commit、构建过程和镜像digest；不假定公开上游就是部署包装层。
2. 现有 `get_kline` 单票HTTP、批量SDK的真实调用链、SDK参数和原始返回形状。
3. 现有MCP框架/协议版本、tools/list的实际schema、超时/并发与会话处理方式。
4. 原始量额单位、来源、历史范围和源发布时间可取得程度；不能猜100倍或用查询时间代替发布时间。

如果缺少源码/部署访问，只暂停依赖这些访问的服务修改；可以先建立契约测试，不虚报部署修复。

## 建议实施顺序

1. 先用 `legacy_reproduction` 复现批量空数据及单元素封装问题，定位根因并留下回归。
2. 建立显式contract_version分支，保持旧版；实现规范证券键、统一data/meta和schema。
3. 完成core日K/清单/日历/状态及来源、单位、coverage、limit、hash和快照。
4. 加入故障注入、有限并发/服务端期限、轻量状态与恢复测试。
5. 运行离线契约校验和服务端真实/注入测试，按编号交付结果，实际部署遵循该环境的发布授权与回退流程。

不要只修limit=0后就宣告完成：历史实测limit=10的多证券批量同样为空。
不要把 `source=http/sdk/warehouse` 当成原始提供者，也不要把unknown补成成功。
不要把修改版本号、健康通过或单票有数据当作批量和完整范围通过。

## 必须返回的交付清单

- 服务版本、commit、镜像digest、访问地址、公开配置和可回退版本。
- 代码改动摘要、真实根因证据，以及旧版兼容检查。
- 与本目录一致的schema和合同修订；任何必要变更都附diff与消费方影响。
- `core_daily_v1` 和扩展支持矩阵，明确历史范围、单位、原始来源、未解决限制。
- 按C01—C24与X01—X05编号的PASS/FAIL/NOT_RUN报告、phase与逐断言证据。
  服务阶段完成C01—C22的服务责任；C23—C24属于本项目后续接入，明确NOT_RUN，不当作服务交付失败或项目已通过。
- 至少一份完整、一份部分失败、一份完全失败的已解包v3响应，和外层MCP一致性证据。
- 慢调用、超时、并发满载后健康及行情恢复的测试输出。

交付应明确区分“服务端已实现/已部署/已验收”和“本项目尚未适配/尚未切换”。
本项目会据同一合同修改现有客户端和采集脚本，再独立联合验收与晋升。
