## 2. 上游依赖（free-stockdb 引擎）

> 上游是数据层的 provider，**不是架构依赖**，但它会静默变更资产/协议/语义。
> 本节的雷区清单与 `docs/release-policy.md` §6 的 SOP 互补：**SOP 讲怎么换，本文记会踩什么**。

### 2.1 引擎 HTTP 协议 JSON → MsgPack（0.10.29）

**症状**：`health.coverage` / `code_stats` / 完整性验证等字段全变 `None`，同步校验失败；
面板大面积 `null`，但引擎进程活着。

**根因**：引擎 0.3.5 起 HTTP 响应从 JSON 改为 MsgPack，**请求侧无开关**。

**判据**：`curl -i "http://127.0.0.1:7899/?cmd=get&t=股票代码"` 看 `Content-Type`，
非 `application/json` 即中招。

**处置**：`storage/providers/free_stockdb.py` 的 `fetch` 按 Content-Type 嗅探 →
`storage/providers/msgpack_lite.py` 解包 → 再 JSON 序列化回现有调用链。

**教训**：协议层变更表现为「字段变 None」而非报错——上层任何"取不到就是 None"的
兜底都会把协议故障伪装成数据缺失。

### 2.2 SDK 区间语义变更 → 全市场快照退化（0.10.33）

**症状**：全市场快照从 ~5170 只掉到 **~50~100 只**；仓库沉淀零星行、打板清单漏检。
**单只 `get_kline` 完全正常**——单只调用掩盖了链路故障。

**根因**：引擎二进制重传后，批量 SDK 的区间语义变了（原按区间返回，改后需
`start == end` 才返回当日全量）。

**判据**：对比「单只取数正常」与「全市场快照只回几十只」——两者同时出现即指向批量通道。

**处置**：批量 SDK 改用同日区间 `start == end`；旧语义顺延一日作回落。
**换引擎二进制后必须回归全市场快照链路，不能只测单只调用。**

### 2.3 pybao 惰性 `QueryResult` 被当普通容器（0.10.41）

**症状**：mydb 数据**写进去了却读不出来**——全表读全空、键列表变成
`[' ', 'M', 'a', 'i', ...]`（逐字符）、`for v in rd.vals(...)` 恒 0 行、
`.keys()/.all()/.len()` 返回错误文案 `'Missing required parameters'`。

**根因**：`QueryResult` 是惰性对象，**`.do()` 才取原生数据**。当成 list/dict 迭代
拿到的是错误文案的字符串。

**处置**（三处收口）：`mydb_store._rd_to_py` 补 `.do()` 分支、`pybao_tools.rd_keys`
经 `_to_py` 归一、`hk_klines` 走 `_rd_to_py`。

**铁律**：**凡 rd 返回值必先过归一函数，禁止直接 `list()/dict()/for` 迭代 QueryResult。**

### 2.4 mydb 键形态：段式 vs 拼接（0.10.41）

**症状**：`get(table, "00700:20240828")`（拼接）与带表名整串**恒返回 `[]`**；
命中的是**三段** `get(table, code, date)`。单段键（`打板指标`/`自定义`）才用两段。

**处置**：`mydb_key_candidates` 逐个试，首个非空即返回；剥表名前缀只在首段
确属已登记前缀时才做。

**铁律**：**实测为准，勿按直觉写键形。**

### 2.5 上游重传资产 → pin 失效（0.10.31）

**症状**：重建镜像卡在 `sha256sum -c /tmp/pkg.tar: FAILED`——URL 不 404，但 tar 哈希变了。

**根因**：上游**同 tag 重传**资产（0.3.5 在 09-08 重传过一次：同 tag、同
`sync_client_0.3.5`、同 MsgPack 协议，服务端二进制重建 → 双平台 tar 哈希变化）。

**处置**：按上游 `SHA256.txt` + GitHub API digest + 本机下载实测**三方一致**重新 pin。
流程见 `docs/release-policy.md` §6.2。

**遗留**：资产指纹探测（0.10.40）已做，但只覆盖 `/releases` 列表端点——
**同名 tag 重传的资产指纹未比对**，目前仍只能靠同步失败被动发现。

### 2.6 Dockerfile `ENV` 位置（0.10.37）

**症状**：构建报 `failed to solve: no build stage`。

**根因**：`ENV IMAGE_TAG=${VERSION}` 写在首个 `FROM` **之前**——`${VERSION}` 是构建期
ARG，只能在 stage 内展开。

**处置**：`ARG VERSION` + `ENV IMAGE_TAG=${VERSION}` 都放进**最终 stage 内部**。
（镜像 tag 与引擎版本是两个维度，见 `docs/release-policy.md` §4。）

### 2.7 上游设备验证 → auth failed（0.10.28 / 0.12.1）

**症状**：同步连续多日失败，日志出现 `状态：网络不通 → auth failed`；**同步器退出码仍是 0**。
上游 `sync_url.txt` 未动，是上游侧设备验证过期。

**处置**：这是上游侧问题，本仓库不写适配层——等上游恢复即可；本地侧靠
§3.1 的「次日追平即撤」保证恢复后面板不留残留红点。

**重要**：上游会**静默删除/替换 release 资产与同步域名**（08-27 实证），
所以镜像 tag 与同步源都可能突然失效，不要以为是本地问题。

### 2.8 镜像更新入口：禁 `dns.novapi.cc`，用 `http://ad.123128.xyz`（上游 10-08 公告）

**规则**：**禁止直接用 `dns.novapi.cc` 更新**——所有客户端都打它，**会把源站拉满**。
上游已改回 **`http://ad.123128.xyz`**。

**判据**（2026-10-20 实测）：

```sh
curl -s -o /dev/null -w "%{http_code} -> %{redirect_url}\n" --max-time 12 http://a.123128.xyz/
# -> 302 -> https://dns.novapi.cc/     ← 走 novapi = 打在被禁的源上
```

**处置**：
- **同步源**：`/data/sync_url.txt` 的每日增量源（source 1，`always`）用
  `http://ad.123128.xyz always`；source 0（`ah.`，全量 `once`）本次未动；
- **镜像页探针**：`MIRROR_PAGE_URL` 默认值**不得**是 `a.123128.xyz`（它 302 到 novapi）——
  0.12.14 起默认 `http://ad.123128.xyz`。

**源可用性的正确判据 = 「同步有没有成功」，不是「根路径返回什么」**：

```sh
grep -aE 'Success: 同步已|数据源失败|正在验证设备状态' /data/sync.log | tail -6
```

- 镜像是**按需路径取文件**的，**根路径返回 404 是正常的**（`/manifest.txt` 也在子路径）；
- **http/https 表现不一致**（同一路径 http 能返回、https 超时，或反之），且上游整体在抽风；
- → **单次探测结果不能用来判定「源挂了」**。

**⚠️ 「源整体消失」的结论必须跨时段复验**（2026-10-20 教训）：
同一天 **15:50** 同步报 `auth failed / 状态:网络不通` → **16:37** 同一源 `状态:有效`
→ **18:16** 同步 100% 完成、引擎推进到 `20261020`。
**一次失败 ≠ 源挂了。** 判定前至少隔时段重试若干次（详见 `engine-data-stale.md` §9）。

## 3. 面板与部署

### 3.1 告警销账：条件式投影 + 次日追平即撤（0.10.36 / 0.12.1 / 0.12.2）

**症状**：上游 4+ 交易日的故障已恢复、数据已追平，但**告警中心的红点长期挂着**，
必须手工 `/api/alerts/clear`。

**根因**：`Alerts.add` **只有 add 没有撤销通路**——告警是一次性记录，而故障型告警的
恢复不在产生告警的那个进程里发生。

**处置（三层）**：
1. **`Alerts.resolve(source, prefix, before=)`**——条件恢复即撤警；
   `before` 只撤 ts 严格早于该日期的条目（**次日追平即撤**）。
2. **文案前缀先行**：告警文案改为「沉淀就绪门未过（<date> ≤20:00）：<reason>」
   这种**前缀开头**的形式——日期开头导���的旧文案匹配不到 prefix。
3. **自动销账接线**：次日任务全绿时自动撤旧告警
   （`warehouse_run(require_today=True)` / `hk_run_sync` 清单全绿）。

**语义边界**：
- 当日新挂的告警**保留**——当日还在 20:00 演进窗口内，过早销撤会丢证据；
- **手动路径不销账**（`require_today=False`）——数据面未确认当日追平，
  销撤进行中的故障告警等于丢证据；
- 部分失败（`ok=False`）不销账——超时告警声明的清单未全部成功，无销账权。

### 3.2 驾驶舱与告警中心是两条管线（0.12.2）

**症状**：告警中心已清零，驾驶舱顶部仍挂「需处理 27 项」红卡。

**根因**：驾驶舱聚合的是 `sync_history` 的**逐条分类**（`sync_failure_class`），
与告警中心是两条独立管线——清一边救不了另一边。
且 `has_later_success` 只看**当日**有无后续成功，**跨天**的追平救不回失事日。

**判据**：失事日失败条目 `needs_action=true` 且 classification 非 `self_healed`
→ 属此坑。

**处置**：`load_timeline` 预扫全局成功点（exit=0 + verified=pass，按 ts 排序）；
失败条目若在**之后**存在成功运行且 `data_latest` **严格前进**（双方均需 8 位日期
才比较）→ 归类 `self_healed`（复用既有 class 名——新 class 串会被前端旧兜底误判成 err）。

**保守分支**：水位**同值**的成功**不**销账（不误销）。

### 3.3 `.env` CRLF → POST body 静默变空（0.10.45）

**症状**：`POST /api/auction/run {"backfill": true}` 返回"成功"但**实际零目标**；
所有 POST 的 body 参数静默变默认值。GET 接口与 `/mcp`（不带 token 头）完全正常
——极具迷惑性。

**根因**：`.env` 是 CRLF 行尾，shell 里 `cut` 取出的 `WEBUI_TOKEN` 尾部带 `\r`；
放进 `X-StockDB-Token` 请求头后，头值里的裸 `\r` 被服务器当成行结束，
**其后的 Content-Type / Content-Length 头全部丢失** → `_read_json` 读到 length=0
返回 `{}` → **所有 POST body 参数静默变默认值**。

**判别法**：`POST /api/auction/run {"task":"bogus"}`
- 回显 `非法 task ''` = **body 丢失**
- 回显 `非法 task 'bogus'` = 正常

**预防**：读 token 后一律 `tr -d "\r\n"`；`.env` 转 LF。
（已发生过的实例：`/vol1/stockdb/.env`，备份 `.env.bak-crlf-20260919`。）

### 3.4 文件清单式部署漏目录（0.10.39 / 0.10.44）

**症状**：代码明明改了并提交，**部署后行为没变**。

**根因**：部署清单按文件逐个列，**漏了目录**（`services/` 整个漏掉；
`interfaces/web/routes.py` 漏掉 → 端点 404）。

**处置**：部署清单**按目录同步**，不按文件列表。同步后逐文件 `sha256sum` 比对
（用 `git blob` 直出 LF，避开工作区 CRLF，见 §3.7）。

### 3.5 `sudo` 抢 stdin 挂死（2026-09-14 实测）

**症状**：SSH 通道卡满 120s 超时；`sudo -S -p ''` 把后续命令内容当密码读了。

**根因**：**同一条 exec 里出现第二个 sudo、或与其它读 stdin 的命令串联**，
就会互相抢输入。

**铁律**：
- **一次 exec 一个 sudo**；
- 要装多个文件就写成脚本文件，`sftp.put` 上去再
  `sudo -S -p '' sh /tmp/xxx.sh`（脚本从文件读，不与密码抢 stdin）。

### 3.6 容器启动即退出（0.5.0 起的发行版约束）

**症状**：容器一直 `Restarting` / `Exit` 循环。

**发行版行为约束（已实测二进制确认）**：
- **conf 必须作为命令行参数**：用法 `stockdb [-d] /path/to/conf`，
  不传 conf 直接 `error loading conf file` 退出；
- **pidfile/log 必须可写**：conf 里 `pidfile`/`output` 指向只读路径会写失败退出；
- **数据目录硬编码绝对路径** `/data`（行情）、`/mydb`（私有库），由 compose 卷挂载。

**排查顺序**：`docker compose logs stockdb` 看退出原因 → 端口占用（换宿主端口
`17899:7899`）→ 数据卷权限（`./data` 容器内可写）。

**另见**：fnOS 卷会**丢执行位**——`entrypoint.sh`/`dev.sh` 的 `+x` 可能在 clone/解压后
消失，重建容器即启动失败。同步一律用 `install -m <mode>` 显式带权限（不要 `cp`）。

### 3.7 工作区 CRLF vs 仓库 LF（2026-09-14 实测）

**症状**：按字节上传后 NAS 上 `sha256sum` 与本地不等，但 `git status` 干净、
`git diff` 为空。

**根因**：本机 `core.autocrlf=true` → git 存 LF、工作区检出 CRLF。部署脚本按**字节**
上传工作区文件 → NAS 上是 CRLF。

**判据**：**`git status --short` 为空 = 内容一致**；`sha256sum` 不等 = 行尾/权限差异，
**别据此判断"部署没生效"**。运行时代码不受影响（Docker `COPY` 逐行处理，
CRLF 无副作用——已实证同版本两次构建产物 digest 不同但行为一致）。

**预防**：要字节一致就用 `git blob` 直出 LF（`git cat-file blob <sha>`）。

### 3.8 卷上 `find` / `docker system df` 很慢

**症状**：几十秒到分钟级，容易误判成"SSH 断了"。

**处置**：查目录就指定深度（`find <dir> -maxdepth 2`），查镜像用
`docker images --format`（别用 `docker system df`），别做全盘扫描。

### 3.9 compose 用精确 tag 而非 `:latest`（0.10.44 起）

**症状**：改动后 `docker compose up -d` 仍跑旧镜像。

**根因**：compose 写 `:latest` 时，若新镜像未真正构建/推送，up 会继续用旧镜像。

**处置**：compose 用**精确 tag**（`image: stockdb-ai:0.12.5`），改动后改 tag 再
`build` → `up -d`。

### 3.10 旧本地镜像会自行消失——**回滚点不是镜像**（2026-10-20 实测修正）

> **本条修正了此前 runbook 里「回滚点会被 `docker rmi` 清理掉」的旧说法**——
> 那个说法不准确。真实机制见下。

**实测（2026-10-20）**：NAS 上 `stockdb-ai` 的旧版本镜像（0.11.0~0.12.4 共 7 个）
**全部查不到**（`docker image inspect` 报 MISSING）。但：

| 假设 | 核查结果 |
|---|---|
| 是 `docker image prune -f` 删的 | ❌ 排除——prune 前（15:20 盘点）旧镜像**已经**不在；12:58 探测时 0.11.1/0.11.0 就已消失 |
| 是 `docker compose up -d` 删的 | ❌ 排除——受控实验（probe:v1/v2/v3 + compose up 换 tag）中 v1 全程幸存 |
| 是别的项目共享层被回收导致 | ⚠️ **最可能**——build 输出显示 37 步全命中缓存（0.2s），旧镜像的层被新镜像复用；Docker 28.x + overlay2/btrfs 下旧 tag 的 manifest 引用关系被打断 → tag 镜像查不到 |

**结论**：**本地构建的旧镜像是缓存产物，会随新构建/GC 自行消失，不能当回滚点。**

**真正的回滚点（两个，都已验证）**：

| 载体 | 验证 |
|---|---|
| **`src-backup-<date>-<ver>.tgz`** | ✅ 完整（548 文件；`docker/` 7 项、`stockdb-ai/app.py`+`config.py` 各 1、`webui/` 99 项；内含 config.py 版本号正确） |
| **git tag `vX.Y.Z`**（99 个） | ✅ 完整——发布物标记，回滚的版本锚点 |

**回滚路径（可行，已验证前提）**：

```bash
# 1) 恢复源树
tar xzf /vol1/stockdb/src-backup-<date>-<ver>.tgz -C /vol1/stockdb
# 2) 改 compose tag
sed -i 's|image: stockdb-ai:X|image: stockdb-ai:Y|' /vol1/stockdb/compose.yaml
# 3) 重建 + 起
cd /vol1/stockdb && docker compose build && docker compose up -d
```

**纪律**：**`src-backup-*.tgz` 要按「保留最近 N 个」策略管理**（N≥3）——
它们是唯一的本地回滚载体。旧镜像不必刻意保留（会自行消失，留着也没用）。
**清理镜像时别用 `docker image prune -a`**（会删无容器引用的所有镜像）。



### 3.11 镜像构建进度条刷爆 SSH 缓冲（0.12.1）

**症状**：`docker compose build` 期间 SSH 被断连，镜像未产出，线上跑的还是旧版。

**处置**：构建输出重定向到 `/tmp/build_XXXX.log`，**只回传结果行**。

### 3.12 点击多了全站「无法访问」（0.9.11 / 0.9.12）

**症状**：进程活着、无错误日志，但**请求排队/阻塞累积**，全站"点击多了无法访问"。

**三个确定性病灶**：
1. **HTTP 并发无上限**：`ThreadingHTTPServer` 每请求一线程，慢操作排队时线程
   无限堆积，最终新请求挂起。→ `_BoundedHTTPServer`（信号量限并发 64，
   **超限快速断开保活而非排队**；`daemon_threads=True`；listen backlog 64）。
2. **backup `VACUUM INTO` 持业务锁**：主连接 `_lock` 内复制全库（NAS 磁盘慢时
   数十秒），期间全部 SQLite 访问阻塞。→ 备份改**独立连接**执行
   （WAL 模式在线备份由文件级锁保证一致性，不占业务锁）。
3. **mydb_read 全表列取连续持锁**（详见 §6.4）。

**排查手法（冻结时定位卡点，无需重启）**：
`docker exec stockdb sh -c 'kill -USR1 $(pgrep -f "python /opt/webui/app.py")'`
→ 全部线程栈打到 docker logs。

**并发治理模型见** `docs/runtime-model.md`（Little's Law + 熔断/信号量/单飞）。

### 3.13 外部依赖：NAS 的网络路径会断（2026-10-20 实测）

**症状**：`ssh 192.168.50.146` 超时 / `curl NAS:8081` 连不上 / 部署脚本报
连接失败——**但 NAS 本身没坏**（Tailscale 地址 `100.66.1.5` 可能仍通）。

**根因**：**NAS 走 WiFi 挂在 iStoreOS 的 `br-proxyap`（192.168.50.0/24）网段上**。
本机若切到别的网络（有线 `192.168.31.x`），那个网段就不可达——**NAS 看着像挂了，
其实是网段隔离**。

**判据**：

```sh
# 1. NAS 局域网 IP 通不通
Test-NetConnection 192.168.50.146 -Port 22
# 2. Tailscale 通不通（区分「NAS 挂了」vs「网段隔离」）
Test-NetConnection 100.66.1.5 -Port 22
# 3. iStoreOS 的 WiFi 网桥状态
ssh root@192.168.31.100 "ip -br link show br-proxyap"
```

**处置**：
- Tailscale 通 → 改用 Tailscale 地址部署（**可靠通道**，与网段无关）；
- Tailscale 也不通 → 是 iStoreOS WiFi 掉了 → 排障手册**在本仓库之外**
  （`~/Desktop/home-ops/istoreos-wifi-troubleshooting.md`，非项目内容）；
- 长期解法：给 NAS 接**网线**（`br-lan` 侧 `192.168.31.x`），或让 NAS 也装
  Tailscale（它已有 `100.66.1.5`，说明已装）。

**教训**：本项目的生产环境**不只有「仓库 + NAS」两层**，中间还压着
「iStoreOS 路由 + WiFi 网段」这一层外部依赖——**它不出现在任何代码或文档的
依赖清单里，却能让整个部署链路失效**。这类「环境拓扑依赖」应当显式登记。

### 3.14 NAS 源树会漂移——**部署前必须全量对齐 + 逐文件 sha256 核验**（0.12.15 实测）

**背景**：NAS 的 `/vol1/stockdb/src` 是**构建用源树**（不是 git 仓库，`.git` 已删）。
历次部署只同步「与上个版本有差异的文件」，**累积下来会漂移**——2026-10-20 部署
0.12.14 前实测：**188 个文件里 115 个与仓库不一致**。

**坑一：CRLF 漂移（115 个文件）**
- 现象：NAS 上的 `.py` 文件带 `
`（从 Windows 工作区同步的），仓库 blob 是 LF；
- 判据（逐文件对照）：
  ```sh
  # NAS 侧
  sha256sum src/stockdb-ai/core/__init__.py
  tr -d '\r' < src/stockdb-ai/core/__init__.py | sha256sum   # 去 CR 后应 == 仓库 blob
  # 本地侧（仓库 blob 的真值）
  python .env-support/git_tree_manifest.py HEAD /tmp/local.txt
  ```
- 危害：运行不报错（Python 吃得下 CRLF），但**镜像内容与仓库不一致**，
  出问题无法用「仓库版本」对齐复现。

**坑二：`git archive` 会跟着 `core.autocrlf` 转 CRLF**
- Windows 上 `core.autocrlf=true`，`git archive` 产出的是 **CRLF** 版本；
- **必须显式关掉**：
  ```sh
  git -c core.autocrlf=false -c core.eol=lf archive --format=tar -o src.tar HEAD
  ```
- 核验（PowerShell 里 `tar -xOf` 会把行尾规整掉，**测不出 CR**，要用字节级方法）：
  ```python
  tarfile.open('src.tar').extractfile('stockdb-ai/app.py').read().count(13)  # 必须为 0
  ```

**坑三：`tar -czf` 的条目名相对 `-C` 目录 → 解到「旧包」**
- `tar -czf out.tar.gz -C dir file` 存进去的条目名是 **`file`**（不是 `dir/file`）；
  NAS 上 `tar -xzf` 落在**当前目录**，而 `find` 可能捞到**上一次残留的同名 tar**——
  **两次解包结果完全一样**，极具迷惑性（本次连续两次都是 CRLF，才暴露出来）；
- 处置：解包前**先删残留**（`rm -rf /tmp/.tmp-ssh /tmp/src_head.tar`），
  解包后**打印 tar 的 sha256 与目标路径**核对，别用 `find` 猜。

**坑四：`__pycache__` 会被打进镜像**
- `.dockerignore` **没有**排除 `__pycache__`（它只排了 docs/CHANGELOG 等）；
  而 Dockerfile 是 `COPY stockdb-ai/core/ /opt/webui/core/`——**整目录拷贝**，
  源树里的 122 个 `.pyc` 全部进镜像；
- 处置：部署前 `find src -name '__pycache__' -prune -exec rm -rf {} +`，
  同步后再断言 `find src -name '*.pyc' | wc -l` = 0。
  （镜像内运行时生成的 `.pyc` 是容器可写层的产物，与此无关。）

**正确姿势：全量对齐 + 逐文件 sha256 核验**

```sh
# 1) 本地出「仓库 blob 真值」清单（LF）
python .env-support/git_tree_manifest.py HEAD /tmp/local_head.txt
# 2) 出包（关 autocrlf）
git -c core.autocrlf=false -c core.eol=lf archive --format=tar -o src.tar HEAD
tar -czf src.tar.gz -C <dir> src.tar
# 3) NAS：备份 → 解包（先清残留）→ 删多余文件（archive 里没有的）
tar --exclude='__pycache__' -czf src-backup-<date>-<旧版本>.tgz src
# 4) NAS：逐文件 sha256 清单，与本地清单 diff
cd src && find . -type f -print0 | xargs -0 sha256sum | sed 's#  \./#  #' | sort -k2 > /tmp/nas.txt
# 5) 判定：仅 NAS 多出 0 / 仅仓库有 0 / 内容不同 0  → 才允许 build
```

> **判据是「188/188 字节级一致」**，不是「我同步了 3 个文件」。
> 增量同步 + 不核验 = 不知道镜像里到底是什么。

## 4. 同步与调度

### 4.1 同步器退出码陷阱（0.8.17）

**症状**：认证/连接失败时同步器**返回退出码 0**——若不识别失败输出，
会把失败掩盖成 `None > 0` 崩溃或"成功但无数据"。

**处置**：`app._sync_failure_reason(stdout)` 先从**输出文本**识别失败原因，
再判退出码。`_sync_effective(before_date, after_date, counts)` 复核水位是否真前进。

### 4.2 晚到自愈与「就绪门」（0.10.13）

**背景**：镜像晚于 15:50 发布当日日K → 当日数据没到位 → 沉淀就绪门 20:00 未过
（error 告警）→ 次日追平后告警仍挂面板。

**三钩子**：滞后重试（stale-retry）+ 补沉淀（catchup）+ 晚间兜底告警。

**语义**：**次日追平即撤**（见 §3.1）——故障完案以数据运行为准，不以"当天没成"为准。

### 4.3 调度守卫要持久化（0.10.35）

**症状**：晚间重启后**采集再次触发**，采到收盘价冒充开盘价 → 对账全红
（一次性挂 37 条「竞价/开盘偏差」误报）。

**根因**：采集守卫是**纯内存**的（`auction_fired`），进程重启即清空。

**处置**：守卫落盘（`fetched_at` 保持不变 = 已采集过）。
**采集只允许在 `[AUCTION_COLLECT_TIME, AUCTION_COLLECT_DEADLINE]` 窗口内执行**
（默认 09:26~09:30）——过了开盘就是盘中/收盘价，**宁缺勿错**。

**判据**：`fetched_at` 变了 = 窗口外被误采。

### 4.4 打板收口要等数据到位（16:30 收口）

**语义**：收口前校验 `data_latest_date >= D`，未就绪则**推迟重试**——
用未收盘/未同步的数据收口必然全红。

## 5. 仓库层（Parquet + DuckDB）

### 5.1 WAL 是数据库的一部分，不是日志（0.11.1）

**症状**：`warehouse.duckdb` 的 mtime **冻结在 N 天前**，此后所有写入都积在
`.wal`（实测 749 KB / 7 天）。**任何"只拷 `.duckdb`"的裸恢复/取证/演练会静默
退到上一次 checkpoint**——巡检读副本得 `watermark:daily=20260923`，实连读才是
`20260930`，差点误判成"水位线停止推进"（而面板全绿）。

**根因**：DuckDB 1.5.5 的 `wal_autocheckpoint` 默认 **16 MiB**，而仓库日增量仅
~0.1 MB → 自动 checkpoint **日常从不触发**，唯一触发时机是引擎干净关闭。

**关键反转（教训）**：**备份链路本身是好的**——`backup.py` 走独立连接 +
`COPY FROM DATABASE`（逻辑快照），产物离线可读且与实连逐项一致。
坏的是**裸文件语义**：`.duckdb` 单文件 = "上一次 checkpoint 的状态"，
只有 `.duckdb` + `.wal` 才是"当前状态"。
**正确实现的备份掩盖了错误的文件直觉。**

**铁律**：
1. 裸拷一律 `.duckdb` + `.wal`（+ `-shm`）**成对**，单拷主库等于回到过去；
2. 离线读副本若水位/计数"停在某天"，**先怀疑 WAL 未收口，别当业务故障**
   （判别：主库 mtime 远旧于 `.wal` mtime）；
3. 沉淀收尾会自动 `CHECKPOINT`（`backup.checkpoint_duckdb`），`/api/diag` 的
   `warehouse_db` 项透出主库/WAL 新鲜度（`stale` = WAL ≥ 主库 10%）；
4. 手动收口**只能在应用进程内**发 `CHECKPOINT`——独立进程（`docker exec python`）
   会被实例锁挡住（`Conflicting lock is held in ... (PID 59)`，0.01s 失败）。

**顺序硬约束**：沉淀收尾**先备份、后收口**——反序最坏留"备份停在旧水位"的窗口，
本序最坏只是 WAL 多留一天。

**同款语义**见 `research.db` 的 `-wal/-shm`。

### 5.2 水位线越过的中间空洞（0.10.45）

**症状**：`v_daily` 从 09-14（5173 行）直接跳到 09-16（5171 行），**中间 09-15
整天缺失**；打板日检 0915 只有 collect 无 close/沉淀记录，**W38 周K 被完整性校验
卡住 4 天**（`watermark:week` 停在 0911）——**面板却全绿**。

**根因链**：09-15 上游镜像故障 → 当晚 6 轮 stale-retry 全停在 `data_latest=20260807`
→ 沉淀就绪门 20:00 未过 → 09-16 16:22 追平后，调度沉淀 `days=1` **只写最新日**，
**水位线越过 0915**。晚到钩子 `maybe_catchup_sediment` 同为 days=1 且仅在
`watermark < latest` 时触发——对水位线之下的中间日空洞是**盲区**。

**处置**：`services/warehouse_tasks.maybe_backfill_gaps()` 缺口守卫——调度沉淀
成功收尾后调用，自水位线向下回看**有界窗口（5 个交易日）**，发现"无分区且无
`empty:` 标记"的洞：
- **引擎侧探测先行**（快照 `limit=0` 与沉淀通道同源）：有 TRADED 点才回填；
- 无数据则投 warn 告警待次日再探，**绝不写 `empty:` 标记**（见 §5.3）；
- 回填同步执行 `warehouse_run(days=len(可填洞), backfill=True)`，水位线只前进；
- **告警是条件式投影**：洞存在才挂，全部落盘对账后 `resolve` 撤回。

**窗口必须有界是硬约束**：backfill 的 days 语义在"洞数 < days"时会扫到
`_BACKFILL_FLOOR`（2000 年），fnOS 慢卷上是分钟级 stat 风暴。

**遗留**：`empty:` 误标的清理仍归人工（需判断力），守卫只认
"无标记、无分区、窗口内交易日"的洞。

### 5.3 `empty:` 空交易日标记会挡住追平后的回填（0.10.6 / 09-08）

**症状**：某天被标了 `empty:`（空交易日），但后来引擎侧其实有数据 →
**该天永远不会被自动回填**。

**根因**：`empty:` 是**当时的判断**（那会儿拉不到数据），不是永久事实。
一旦误标，后续所有"这天空着"的逻辑都会跳过它。

**处置**：误标清理归人工（需判断力）。守卫**只认"无标记、无分区"的洞**，
不主动写 `empty:`。**"拉不到就跳过该日"是对的，标成"确定为空"是错的。**

### 5.4 某列整列 NULL —— 先分类再判故障（0.10.44）

**症状**：`v_daily.pct_chg` / `amplitude` 整列恒 NULL（5173 行/日全空），
而同两列在周K/月K 里正常有值。同一个字段名两张表两种状态，
排查者第一反应必是"数据丢了"。

**根因**：**不是引擎没给**——引擎单日 bar 实测带 **21 键**（含 pct_chg/amplitude/
turnover/vol_ratio/pb/pe_ttm/市值股本），是快照适配函数 `_point_snapshot_item`
用**手写清单**只挑走 11 键，其余在进入 sink 之前就被丢掉。

**排查纪律（daily 26 列三分类）**：

| 类别 | 列 | 空意味着 |
|---|---|---|
| 引擎 bar 原生 | code/name/is_st/OHLC/prev_close/volume/amount、turnover/pct_chg/amplitude/vol_ratio/pb/pe_ttm/市值股本 | **bug**（适配层丢字段） |
| 任务层注入 | date、prev_close | **bug**（任务层没注入） |
| 本地物化 | adj_factor / open_fq / high_fq / low_fq / close_fq | **设计内**（因子/事件未就绪，不编值） |

**铁律**：两类现象相同、性质相反——**别再用「引擎没给」当万能解释**，
先实测引擎 bar 的键位清单（`cmd=get` + 批量 SDK 双通道各测一遍）再定性。

**已决**：不为这两列重写历史（facts 只增不改，为两列重写 200+ 个不可变分区
风险收益不成比例）。新数据从部署次日沉淀起自动带上，历史分区保持 NULL。

**口径警告**：引擎 `pct_chg` **保留 2 位小数**（600000 = 1.51），本地公式给
1.51187905——**不要用本地公式"修正"引擎值**，否则日K/周月K/引擎三处口径不一致。

### 5.5 全表对账被行数上限截断 → 假不一致（0.10.x 两次踩同一坑）

**症状**：全表对账"不一致"，但实际数据没问题。

**根因**：`run_sql` 结果行数上限 5000（`WAREHOUSE_ROW_CAP`）**静默截断**，
31 万行被砍成 5000 行去比。

**处置**：**全表对账必须先提高 `WAREHOUSE_ROW_CAP` 再拉数**；或分批拉取后自行拼接。
信封的 `truncated` 标记是唯一信号——**看到 truncated 就不许当全量用**。

### 5.6 仓库写入性能（0.10.34）

**症状**：`write_daily` 16.7s、`write_codes` 23.5s——逐行 `executemany` 绑定。

**处置**：改 CSV 批量导入。实测 **0.313s（~53×）** / **0.068s（~345×）**。

**教训**：日常沉淀 + 周月聚合全受此影响——写入路径的量级问题会放大成"沉淀很慢"
的表象，让人误以为是取数源的问题（见 §7.1）。

### 5.7 回填脚本的幂等跳过（0.10.8 起）

**症状**：跑 `backfill_daily_direct.py` 重灌某天，但**什么都没变**。

**根因**：脚本幂等——**已有分区会跳过**。

**处置**：须先删除目标分区文件再跑，**切勿盲删**（详见该脚本 docstring）。

### 5.8 守卫条件必须用真实数据校准（0.11.2）

**症状**：换源优化上线，**实测耗时与修复前无异**（白跑 70.9s）。

**根因**：守卫判据写成"窗口内每个请求码都必须有行"，而"4 只停牌股"这种常态
直接判假 → 一路退回引擎。而且"全市场默认请求"写成 `codes is None`，
而打板慢路径**自己就把 universe 展开成 5200 码传进来**，等于恰好把要修的调用
拦在门外。

**铁律**：**守卫条件必须用真实数据校准**——常态不该触发整段降级。

### 5.9 接线类改动必须留下可查事实（0.11.2）

**症状**：改了取数源，**面板和日志都看不出**"仍在逐码 HTTP"——静默 except
让接线失败与读数异常都无声。

**处置**：把守卫判定汇总为 `_last_wh_probe` 并经 `/api/diag` 透出
（接线状态 + eligible/缺口数/reader 耗时）。否则每次判断都只能改代码重建镜像盲试
（本次为此多花了 5 轮部署）。

**相关**：接线判据用 `importlib.import_module` + 同文件别名补齐，**不要用
`sys.modules.get()` + 静默 except**——后者让接线"看似成功实则未生效"。

## 6. 本机开发

### 6.1 本机运行配方（缺一不可）

见 `docs/development-guide.md` §2（`STOCKDB_HOST`/`STOCKDB_PORT`/`PYBAO_DIR`/
`PYTHONPATH`/`NO_PROXY`）。最易漏的一条：

**系统代理**：任何 python 网络请求默认走 `127.0.0.1:7890`（Clash），务必设
`NO_PROXY=127.0.0.1,localhost`——否则引擎请求被转发到代理 → 间歇 502 / 5s 超时。

**其它本机坑**：
- **pybao 首次加载慢 / HTTP 502**：SDK 客户端初始化会全表预载复权因子，
  期间引擎忙；预热完成后恢复（避免预热期并发 HTTP）。
- **`rd.keys("*")` / `mydb_tables()` 会挂死**：全表扫描分钟级。生产路径只做
  前缀通配（`rd.keys(table, "code:*")`）。
- **mkdtemp 目录不可写**：Python 3.14 Windows 对 `os.mkdir(0o700)` 施加受限 ACL
  ——仅影响受限令牌环境，真实终端无此问题。
- **DATA_DIR 未显式设置**：Windows 上默认 `/data` 解析到 `C:\data`（本机漂移
  事故源头）。`config.py` 启动即告警；`dev.sh` 固化 `DATA_DIR=../data`。

### 6.2 from-import 快照绕过 patch（0.10.x 教训）

**症状**：测试里 patch 了 `app.xxx` 但用例不生效。

**根因**：`from app import xxx` 在 import 时**快照了函数对象**，
后续 `patch("app.xxx")` 改的是 app 模块的属性，已快照的引用不会跟着变。

**处置**：用例必须走 `app.*`（动态取属性），不要 from-import。
`test_ops.py` 已有守门注释。

### 6.3 模块身份分叉：脚本直跑 vs import（0.9.10 / 0.10.24）

**症状 A（启动即崩）**：`python app.py`（容器 entrypoint）时 `sys.modules` 里没有
`'app'` → `handlers.py` 顶层 `import app` 触发**循环重载** →
`cannot import name 'Handler' from partially initialized module`。
**模块导入方式（`import app` / 测试）此前完全掩盖了该问题**——只有脚本方式才炸。

**处置**：Handler 从模块级移到 `main()` **延迟装配**（app 模块已完整后再 import）。

**症状 B（状态永不可见）**：脚本直跑时本模块叫 `__main__`，`handlers.py` 的
`import app` 会**再载入第二份实例** → 调度线程在 `__main__` 里更新的
`_scheduler_alive` / `_scheduler_heartbeat` / `_sync_state` 对 handlers **永不可见**
（实机实证 `scheduler_alive` 恒 False、调度运行态恒 idle）。

**处置**：单实例别名——脚本直跑时把本模块注册为 `app`，后续 `import app` 拿到
`__main__`（0.10.24 修；0.10.23 的 from-import 修复只解了一半）。

**铁律**：**凡"改了一处另一处不生效"，先查是不是模块身份分叉。**

### 6.4 pybao rd 单连接非线程安全（0.9.11）

**症状**：协议帧交错（2026-08-16 冻结事故同类）——并发读 mydb 时数据错乱。

**根因**：pybao `rd` 是**单连接**，非线程安全；多线程并发访问会帧交错。

**处置**：`_rd_lock` 改 RLock 并收敛全进程——所有 rd 访问经加锁辅助
（`pybao_tools.rd_get/rd_keys`，同进程容器与 app 侧共享同一把锁）。

**相关**：**全表列取时不要连续持锁**——500 键逐键 get 持锁全程（引擎慢时 25s+），
MCP 快速通道/打板任务全部排队。改细粒度持锁（keys 一次、逐键各一次）。

### 6.5 vitest hoist transform 吃掉行尾注释（0.10.27）

**症状**：`vi.mock(...)` 行尾注释被吃掉并连带换行，下一行被拼上来 → rollup 解析错。

**处置**：`vi.mock` 行**禁止行尾注释**（注释写上一行）。

### 6.6 测试日期腐化（0.10.45）

**症状**：4 个时间线用例随真实时间推移**恒红**——固定播种 0904/0907/0908/0909/0911
滑出了 7 交易日窗口。

**处置**：`load_timeline` 抽出可 patch 的时钟缝 `app._timeline_today()`
（与 `_monotonic` 同惯例），用例冻结窗口起点。
**凡写死日期的用例，都要能被时间推过。**

### 6.7 环境变量坏值在 import 阶段崩溃（0.9.11）

**症状**：环境变量写成非数字 → `import` 阶段直接 `ValueError`，
**webui 起不来且无提示**。

**处置**：所有环境变量整数解析经 `config._env_int`——非法/缺失回退默认**并告警**
（此前裸 `int()` 崩溃）。同理 `auction_env_time` 校验 HH:MM 并补零规范化
（`'9:26'` → `'09:26'`——补零前的字典序比较会让 `'10:00' >= '9:26'` 为 False，
调度只在 09:26-09:59 触发、收口永不触发，**静默失效无日志**）。

## 7. 采集链与打板

### 7.1 慢路径瓶颈是取数源，不是算法（0.11.2）

**症状**：打板开盘溢价 60 交易日区间 **70.9s**（另一版实测 75.9s / 68.9s）。

**量化定位**：`query_fullmarket_daily_snapshot` 逐码走引擎 HTTP
（5200 码 × 8 并发 × 每请求 50ms 节流）实测 **68.9s**，而
`compute_board_open_effect_details` 只用 **2.32s**；同一批日K 在仓库里已有
Parquet 落盘，等价取数 **0.05s 计数 / 1.36s 取 538572 行**。

**处置**：慢路径换源仓库（`storage.warehouse.queries.read_fullmarket_daily`），
但守卫要严：
- 仅全市场默认请求走仓库（显式 `codes`/`limit` 是调试小样本，引擎按需取更省）；
- **缺码交引擎补，不整段退回**（停牌股窗口内本就无成交——NAS 实测仓库 5196 /
  universe 5200，4 只停牌）；
- 缺口过大（>1% 或 >50 码，如区间早于仓库覆盖）→ 整段退回引擎。

**换源必须同构**：两条取数源**必须产出同构的 snapshot 与 metadata**——
信封的 `coverage_is_complete`/`formal_usable`/`partial_reasons` 是下游与用户都
依赖的判据，"换源"悄悄改这些字段是真实风险。

**回退不记为 failed**：仓库未命中只是内部取数源回退，计入 `failed` 会把信封染成
`SOURCE_REQUEST_FAILED` + `formal_usable=false`（**假降级**）。来源由
`metadata.data_source` 单独透出。

### 7.2 打板兜底覆盖率护栏（0.10.42）

**症状**：某日竞价只采到 **13 只**，而权威是 **66 只**——清单为空走了兜底现算路径，
但 `coverage.formal_usable` 仍为 `True`（批量通道不报错、无 bar 的代码被归入
suspended）→ **全天无一处告警**。

**根因**：部分快照（当日引擎区间语义退化）；批量通道不报错，
缺 bar 的代码被误归 suspended，于是"覆盖率不足"和"停牌"长得一样。

**处置**：护栏按「**兜底清单 < 前日权威 n_samples × 0.5**」判定，只告警不阻断、
也不自动改写清单。

**判据**：兜底清单条数 vs 前日权威条数——比值 <0.5 即告警（实测 13/66 = 0.1477
触发；66/88 = 0.75 不触发）。

### 7.3 采集窗口与字段位序（0.10.35）

**症状**：采到的"今开"其实是**当前价**——腾讯通道今开取第 5 位，代码取了第 3 位。
晚间重启后再次采集（守卫纯内存已清空）→ 拿到收盘价冒充开盘价 → 对账全红
（37 条误报）。

**处置**：今开取**第 5 位**；采集仅在 `[09:26, 09:30]` 窗口内执行；守卫落盘。

**语义**：采集快照对"开盘价"是**中间态**，对"当日 09:26 的竞价证据"是**终态**——
处理原则是**不删、不改、只转态 + 对账**（captured → reconciled）。

### 7.4 竞价价分母口径（0.8.13 / 0.8.14）

**口径**：溢价分母 = **T-1 收盘价**（除权日也要用 T-1 收盘，不可用交易所调整昨收）。

**根因**：采集表 `prev_close` 在除权除息日是交易所调整昨收，混入分红会失真。

**铁律（0.8.14 血泪教训）**：引擎 `pre_close` 被**未来除权因子回溯污染且不均匀**，
**禁止使用，也禁止统一因子反推**——正确做法是**普通日用上一实际成交日未复权收盘
（lag close）**，除权日才用当日 `pre_close`。

### 7.5 缺失计数守恒（0.9.0 M1）

**守恒等式**：`候选数 = 一字板数 + n_samples + missing_open_count`（单测断言，
防静默丢弃）。

**背景**：0.9.0 之前该语义缺失——板日涨停但指标日无 bar 的股票被**静默丢弃**
（仅 MCP 当日段口径有计数，回填/收口路径未计）。

### 7.6 分位口径（0.8.11 起）

- `rank = (此前 60 个有效观测中**严格小于**当日值的天数) / 60`
- **严格小于**：等值不计入（旧版 count_equal 折半计入已废弃）
- **分母固定 60**：不足 60 个有效观测 → `rank_60d = null`（不硬算近似）
- 强弱标签：`strong` rank≥0.90 / `weak` rank≤0.10 / 其余 `neutral`；rank 为 null → 标签 null
- **无未来函数**：历史回填日无分位是预期行为

## 8. 方法论沉淀（比坑本身更通用）

> **这七条是归纳，不是原文搬运**——每条的方法论表述由我提炼，**但每条都有
> 至少一处事故原文支撑**（括号里的版本号即出处，可回查 CHANGELOG / 台账）。
> 归纳的共性：多数事故的**排查成本远高于修复成本**——根因往往只有一行，
> 但"为什么没早发现"要查好几层。


### 8.1 不得据截断输出下结论（0.11.2）

**症状**：把 `bk_get` 判成"过滤失效"并上报为缺陷。

**真相**：完整解包后完全正确（`银行`→3 板块/42 码、`801760.SL`→1 板块/130 码、
`600000`→所属 10 板块、不存在→0）；pybao `bk.get` 本体实测同样正确
（仅 `None` 返回全量 1337）。误判源于**只打印了响应前 220 字符**，
把 `symbol_count` 字段的 `total: 1337` 与截断出的同一条板块记录
误读成"全量列表"。

**铁律**：**不得据截断输出下结论**——先看全量，再定性。
（同日同类误判共两次，另一次见 WAL 那条。）

### 8.2 降级不等于失败——假绿比假红更危险（0.10.38 / 0.10.39 / 0.11.1）

三个同源缺陷，都表现为"面板全绿但实际有问题"：

1. **`/api/diag` 把网络受限判成系统故障**——`upstream_github` 探针失败
   → `all_ok=false` 整体打红（假红）。改 `ok=True + degraded=True`。
2. **观测项写错属性/路径，异常被 `except` 吞成"状态不可用"**——`ok=True` 故面板
   不红，**静默降级成假绿**。0.11.1 的 `warehouse_db` 首版即此款。
3. **退化条件让故障看起来像正常**——采集不报错但覆盖率 13/66（§7.2）。

**纪律**：
- **降级不计入 ok**，但必须显式标 `degraded` + 写明 `note`；
- 探针失败要区分「系统故障」与「网络受限」；
- 观测项写错时**必须能在 note 里看到**，不能只显示"状态不可用"；
- **盲区成因要写进用例**：本地 `warehouse.duckdb` 不存在 → 该分支被跳过 →
  测试套件放行（0.11.1）。**断言要覆盖"观测项不得异常"且"能取到真值"**。

### 8.3 静默降级是排查的头号敌人（0.11.2）

**症状**：接线失败、读数异常**都无声**——面板/日志都看不出"仍在逐码 HTTP"。

**纪律**：**静默 except 必须留痕**（stderr + 失败状态进观测项）。
"接线类改动必须留下可查事实"——否则每次判断都只能改代码重建镜像盲试。

### 8.4 独立进程 ≠ 运行进程（0.11.1）

**症状**：独立进程（`docker exec python` / 脚本直跑）里 `import app` 拿不到
接线好的注入点（`checkpoint_duckdb=None`），让人以为功能没实现。

**纪律**：**验证期用真实 HTTP + 源树取证**，不要用独立进程 import 的结果下结论。
另见 §6.2 的模块身份分叉。

### 8.5 假绿防线：断言要覆盖"真跑通"，不只是"不报错"（0.11.1）

**症状**：观测项首版写错 → 被 `except` 吞成"状态不可用" → `ok=True` → 面板不红
→ 用例只断言"不抛异常"就放行。

**纪律**：断言必须同时覆盖两件事——
① **不得出现观测项异常**；② **能取到真值**（mtime / WAL 字节数 / 字段齐全）。
并注意本地环境可能整条分支被跳过（本地无 `warehouse.duckdb`），
**要构造能真正跑到该分支的用例**。

**已落地的断言**（可对照 `stockdb-ai/test_ops.py`）：
`test_diag_warehouse_db_probe_actually_runs`（断言 `note` 里**不出现**
「观测项异常」+ 取到 mtime/WAL 字节数）、
`test_diag_hk_sync_probe_actually_runs`（同款纪律，锁「探针真跑通 + 取到清单事实」）。

### 8.6 判别法优先于"看日志"（0.10.45）

**范例**：`.env` CRLF 吞 body 的判别法是发一个**已知非法**的 task，
看回显是 `''`（body 丢了）还是 `'bogus'`（正常）。
**设计"能用请求区分两种状态"的探针，比让人去翻日志快一个数量级。**

### 8.7 制度写了 ≠ 执行了（2026-10-20 实证）

**症状**：`release-policy.md` §4 明写「每版必打 tag」，实际 **17 个版本从未打 tag**
（09-19~10-17 连续 9 版 + 两段更早的缺口，最远回溯到 0.5.0）。
后果：tag 是原生模式下的**唯一发布物**、是回滚的唯一依据——
缺口期间「回滚到上一个已知良好版本」无 tag 可依。

**根因不是"忘了"**——是**跨工具摩擦**：
「合并 PR」在浏览器 UI，「打 tag」在本地终端 `git tag` + `git push`，
每次发版都要切换工具，**跨 17 次全漏**。
凡是「每版必做 X」类纪律，若 X 的动作**跨工具**，就会静默失效。

**判据（三问）**：遇到新的「每版必做」纪律时先问——
1. **X 的判据是什么**？（可客观验证，不能是"记得"）
2. **怎么核对做没做**？（一条能跑的命令 / 一个能看的指标）
3. **动作是否跨工具**？（跨工具 = 高摩擦 = 补判据或补自动化）

**本次处置**：判据 = 版本号单源（`config.py` 的 `WEBUI_VERSION` 首次出现的 commit）；
核对 = `python .github/scripts/audit_tag_coverage.py`（缺 tag 时退出码 1）。
**不自动打 tag**——「哪些 commit 算一个发布」是人的判断（0.11.1/0.11.2 共用一个
commit、0.12.3 跨两个 PR），自动化会越权。

## 10. 变更纪律

- 本书**只增不删历史条目**——坑位记录是事故档案，修了也要留（注明"已修"）。
- 新增条目必须带**出处**（版本号或台账日期），否则读者无法回查证据。
- **代码注释里的实证教训要回写到这里**——注释会随代码演化沉底，
  本书是知识的稳定落点。
- 坑位若与设计文档冲突，以设计文档为准（本书记的是**运维现象**，
  设计文档记的是**口径**）。
- **「环境拓扑依赖」要显式登记**（2026-10-20 新增）——本项目的生产环境不只有
  「仓库 + NAS」两层，中间还压着「iStoreOS 路由 + WiFi 网段」这一层，
  **它不出现在任何代码或依赖清单里，却能让整条部署链路失效**。
  新增外部依赖（NAS、路由器、网段、Tailscale、DNS、代理）时，
  在 §9 遗留表或对应的外部手册里登记它的**失效判据**与**可靠通道**。
- **复验要报「每个口径的实际值」，不能只报一个好看的数**（2026-10-20 新增）——
  本次 0.12.x 的部署复验把 `/api/warehouse/status.watermark_daily`（仓库层水位线）
  当成了「行情数据最新日期」上报，**掩盖了引擎行情已陈旧 2 个月**。
  引擎行情的真实日期是 `/api/health.latest`（走 `data_latest` 探针），
  **两个口径不同，今后必须分别报**。
- **二进制协议下判空用字节数，不用「非空」**（2026-10-20 新增）——引擎 0.3.5 起
  HTTP 响应是 MsgPack，**返回值必然非空**，「非空即有数据」的判断恒为真。
  正确判据：`wc -c` 后 >20 字节才算有数据（1 字节 = 空）。
