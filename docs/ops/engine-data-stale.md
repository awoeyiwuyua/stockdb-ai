# 引擎行情数据陈旧 / 上游源不可达（排障专题，**已恢复**）

> **实测场景**：2026-10-20，NAS 上引擎的 A 股行情只到 **2026-08-07**（滞后 52 个
> 交易日），而仓库层（到 10-19）与港股（到 10-20）都正常。当时判定「**所有上游源
> 不可达**，自动恢复无望」。
>
> **结局（当日 18:16 恢复）**：源是**间歇可达**的——**15:50 失败**（`auth failed /
> 状态:网络不通`）→ **16:37 成功** → **18:16 同步 100% 完成**，引擎追平到
> `20261020`。**「源全挂」是过强结论**，复盘见 §9。
>
> 本书记录「怎么发现 → 怎么定性 → 怎么区分口径 → 恢复路径有哪些 → 恢复后怎么复盘」。

## 1. 三个数据层，别混

| 层 | 存储 | 数据截止 | 与引擎的关系 |
|---|---|---|---|
| **引擎行情** | `/data/data`（LevelDB）+ `/data/data1`（remote1） | 故障期 **2026-08-07** → **已恢复到 2026-10-20** | 本篇主题 |
| **仓库层** | `/data/warehouse/facts/*.parquet` + `warehouse.duckdb` | 2026-10-19 | **独立**，由沉淀任务从引擎快照写入 |
| **港股私有库** | `/data/mydb`（mydb 表） | 2026-10-20 | **完全独立**，走腾讯源，不经引擎 |

> ⚠️ **最容易犯的错**：`/api/warehouse/status` 的 `watermark_daily` 是**仓库层**的水位线，
> **不是引擎行情的日期**。仓库层健康 ≠ 引擎健康。
> 引擎行情的真实日期看 `/api/health` 的 `latest`（走 `data_latest` 探针）。

## 2. 判据：探针口径

`data_latest` 探针（`app.py: data_latest_date`）的查询是**按月前缀通配**：

```
/?cmd=vals&t=日k:000001:YYYYMM*
```

近 95 天 → 扫 `202607 202608 202609 202610` 四个前缀，取返回里的最大日期。

**取 max 即得引擎行情的最新交易日**——这个口径是对的，只是此前被误读成
「仓库层水位线」。

## 3. ⚠️ 判空陷阱：MsgPack 返回值必然非空

引擎 0.3.5 起 HTTP 响应是 **MsgPack 二进制**，不是 JSON。

```sh
# ❌ 错误判据（恒为真）
R=$(curl ...); [ -n "$R" ] && echo "有数据"

# ✅ 正确判据：看字节数
V=$(curl ... | wc -c); [ "$V" -gt 20 ] && echo "有数据"   # 1 字节 = 空
```

> 本次排查中曾用错误判据得出「引擎能查到 20261020、引擎是好的」这一**相反结论**，
> 差点误判为「只有探针坏了」。**二进制协议下必须用字节数判空。**

## 4. 取证清单（按顺序执行，每步都有判据）

### 4.1 引擎实际数据到哪天

```sh
# 逐日探测（vals 与 get 都测）
for d in 20260807 20260810 20260901 20261016 20261019 20261020; do
  N=$(curl -fsS --max-time 10 "http://127.0.0.1:7899/?cmd=vals&t=<urlenc 日k:000001:$d>" | wc -c)
  echo "$d : ${N}B"
done
# >20 = 有数据；1 字节 = 空
```

### 4.2 两个库的状态

```sh
ls /data/data/*.ldb  | wc -l ; ls /data/data/*.ldb  | tail -1    # 主库
ls /data/data1/*.ldb | wc -l ; ls /data/data1/*.ldb | tail -1   # remote1
ls -lt /data/data/*.ldb | head -3    # mtime：全是同一天 = 之后没新文件落盘
```

### 4.3 引擎日志（关键：最早的损坏记录）

```sh
grep -a 'missing files\|remote leveldb unavailable' /data/log.txt | head -3
grep -a 'missing files' /data/log.txt | tail -1
```

> **最早一条的日期 = 故障起点**。本次是 2026-09-11。

### 4.4 上游源逐个探测（**必须从容器内测**，宿主机网络可能不同）

```sh
for u in https://ah.123128.xyz https://ad.123128.xyz https://workbuddy.link; do
  curl -sL -o /tmp/m.txt -w "$u -> http=%{http_code} size=%{size_download}\n" --max-time 20 "$u/manifest.txt"
  echo "   manifest lines=$(wc -l < /tmp/m.txt)"
done
```

**实测结果（2026-10-20 上午）**：`ah./ad.` → `http=000`（连接失败）；
`workbuddy.link` → 404；`a.123128.xyz` → 302 但跟随后 000。
当时据此写下「**没有任何可用源**」。

> ⚠️ **这个结论过强了**（§9 复盘）：**根路径 404/000 都不代表源不可用**——
> 镜像是**按需路径取文件**的，根路径本就 404；**http/https 表现还会不一致**
> （上游在抽风）。**当天 16:37 同一源就成功了。**
> **正确判据是「同步有没有成功」**（`sync.log` 里的 `Success: 同步已`），
> **单次探测不能定性**。

### 4.5 同步器日志（确认是源的问题还是同步器的问题）

```sh
grep -a '=== 同步开始\|=== 同步结束\|失败\|对不齐\|放弃' /data/sync.log | tail -20
```

> **同步器行为是对的**：检测到「N 个文件对不齐」就**放弃本轮**，不强行覆盖已有数据。
> 源恢复了它会自动补齐。**这不是同步器的 bug，是源的问题。**

## 5. 根因链（本次实例）

```
2026-09-06  极空间 → fnOS 迁移，data/ 快照落盘（Aug 23 mtime，此后无新文件）
2026-09-07  上游换域：ah./ad.123128.xyz 换成了别的（sync_url.txt 留了
            .bak-20260907 = workbuddy.link 作对照）
2026-09-11  引擎首次报 data1 Corruption: 10 missing files ← 故障起点
2026-10-20  上午：源探测全部失败，缺 18→4 个文件，同步器多轮放弃
            → 引擎退化为 remote0（只用 data/），行情停在 2026-08-07
2026-10-20  15:50 同步 auth failed（状态:网络不通）→ 16:37 状态:有效
            → 18:16 下载 97.18 MB（006051/006072/006075）Success 100% 完成
            → 热重载 → 仓库推进 20261020（sh/sz 5176 行）→ 追平
```

**关键修正**：缺的文件**不是「永远补不齐」**——**源是间歇可达的**，
源一恢复同步器就自动补齐（本次当天就补齐了 3 个缺失文件）。
**「源不可达」≠「源没了」**（§9）。

## 7. 恢复路径（按代价排序）

1. **等上游源恢复** —— 源回来后同步器会自动补齐 ✅ **本例走的就是这条**：
   源间歇可达，10-20 当天就恢复并追平（**不必一上来就换源**）
2. **换源** —— 改 `/data/sync_url.txt`（release-policy §6.2 的「换域流程」：
   改配置、**不写适配层**）。但需要先找到新的可用源。
3. **用仓库层喂沉淀** —— 仓库层数据比引擎新（10-19 vs 08-07），可作为沉淀的
   数据源。**需改代码**，属设计变更。
4. **ROADMAP §0-2 的「A 股日K 收盘兜底源」** —— 腾讯 `qt.gtimg.cn` 独立于上游引擎，
   正好覆盖此场景。**这是已规划的方向**，且 §0-2 已写明「落独立 dataset
   `facts/daily_provisional/`，绝不写 `facts/daily`」。

## 8. 教训

1. **两个「数据最新日期」口径必须分清**——`/api/health.latest`（引擎）vs
   `/api/warehouse/status.watermark_daily`（仓库层）。**台账里曾把后者当前者记，
   导致「数据正常」的结论掩盖了 2 个月的引擎陈旧。**
   → **今后复验必须两个都报。**
2. **二进制协议下判空要用字节数**，不能用「非空」（§3）。
3. **上游源是不可控依赖**——release-policy §6 已把它列为「三雷」之一，
   但没覆盖「源整体消失」这一情形。**换域/换源是常规操作，不是意外。**
4. **「一次失败」不等于「源挂了」**（本次最贵的教训）——当天**只测了一次**就定性
   「所有源不可达、无任何可用源」，据此写下「缺的文件永远补不齐」；
   **几小时后同一源就恢复并追平**。
   → **判定源可用性看「同步有没有成功」**（`sync.log` 的 `Success: 同步已`），
   **至少跨时段重试若干次再定性**；
   → **根路径 404/000 不能当死源**（镜像是按需路径取文件；http/https 表现还可能不一致）。

## 9. 恢复记录（2026-10-20 当日）与复盘

### 9.1 时间线（NAS 实测）

| 时刻 | 事件 | 出处 |
|---|---|---|
| 上午 | 源探测全失败 → 误判「源全挂」，写「缺的文件永远补不齐」 | 本书 §4.4 / §5 |
| 15:50 | 定时同步 → `正在验证设备状态... 状态:网络不通` → `auth failed`，**退出码仍是 0** | `sync.log` |
| 16:20 | 滞后自检重试（1/6）——**30 分钟后自动再试**的机制救了场 | `sync.log` |
| 16:37 | 同一源 `状态:有效` → `source 0 -> ./data (once)` / `source 1 -> ./data1 (always)` | `sync.log` |
| 17:12 / 17:46 | 继续补齐（18 个 → 4 个 → 3 个待下载） | `sync.log` |
| **18:16** | 下载 **97.18 MB**（`006051/006072/006075`）→ `Success: 同步已 100% 完成！` → `reload 1 ok` | `sync.log` |
| 18:16-18:17 | 引擎热重载 → 复权事件刷新 5176 码 → warehouse 备份 → 仓库沉淀 `20261020`（sh/sz 5176 行） | `sync.log` |
| 复核 | `/api/health` = `{"latest": "20261020", "lag_days": 0, "mirror": null, "status": "ok"}` | webui |

**结论**：走的是 §7 的第 1 条（**等源恢复**），**没换源、没上兜底源、没改代码**。
**同步器的「滞后自检重试（1/6）」是自动化的关键**——它把「源什么时候回来」
与「人工什么时候发现」解耦了。

### 9.2 同步源按上游 10-08 公告改回 http

上游 **10-08 公告**：**禁止直接用 `dns.novapi.cc` 更新**（会被所有客户端反复打到、
**把源站拉满**），官方更新入口改回 **`http://ad.123128.xyz`**。

- `a.123128.xyz` 现在 **302 → `https://dns.novapi.cc/`**（实测），
  所以**任何指向 a. 的配置都在间接打被禁的源**；
- `/data/sync_url.txt` 的每日增量源（source 1，`always`）已由
  `https://ad.123128.xyz always` 改为 **`http://ad.123128.xyz always`**，
  **改后真跑了一次同步验证**：`3/3` 文件下载成功、`Success: 同步已 100% 完成`、
  `reload 1 ok`、引擎仍 `20261020 / lag_days 0`；
- webui 的镜像页探针 `MIRROR_PAGE_URL` 默认值同步改为 `http://ad.123128.xyz`
  （0.12.14）——该主机不再标注「数据更新至」文本，故 `mirror` 字段为 `null`，
  **健康判定不依赖它**（0.10.13 起改用本地探针自检）。

> **http 不是降级，是上游当前的实际入口**：实测同一路径 `http` 能返回、`https`
> 超时（或反之），上游整体在抽风。**别用单次探测定性**。

### 9.3 复盘：这次为什么会误判

| 步骤 | 当时的做法 | 问题 |
|---|---|---|
| 1 | 从容器内探测 `ah./ad./workbuddy/a.` 的 `manifest.txt` | 探的是**根路径**（本就 404）+ **单次** |
| 2 | 看到 `http=000` 就写「源不可达」 | `000` 有多种成因（TLS/超时/抽风），**不等于源没了** |
| 3 | 直接推出「缺的文件永远补不齐」 | **过强**——源是间歇可达的 |
| 4 | 建议换源 / 上兜底源 | 方向没错，但**当时并不必要**（当天就自愈了） |

**制度修正**（已落 `release-policy` §6.5 第 5 条 + runbook §2.8）：

1. **源可用性的判据 = 同步有没有成功**，不是根路径返回什么；
2. **判定「源整体消失」必须跨时段复验**（至少隔 30 分钟~1 小时重试若干次）；
3. **改源之前先看 `sync.log` 的滞后自检重试有没有在跑**——它在自动重试。

> 与本项目此前 3 次误判根因是**同一种错误**：**用一次观测下结论**。
> 区别只在于——这次是**源侧**的观测，彼时是**本地**的观测。
